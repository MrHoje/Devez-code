# 훅 상태 파일 원자적 쓰기 — codex 스피너 stuck-ON

## 증상
codex(및 훅으로 busy 상태를 쓰는 에이전트) 세션이 **작업을 다 끝냈는데 좌측 스피너가 안 꺼짐**(=`IsBusy` 고착). 간헐적.
스피너 표시는 `SidebarView.xaml` 의 `MultiDataTrigger`(`IsEffectivelyHidden == False` AND `IsBusy == True`)로 켜지고, 앞선 트리거가 숨김 세션의 스피너를 강제 Collapsed 한다. 즉 보이는 세션 기준 "스피너 안 꺼짐" = `IsBusy` 가 false 로 안 바뀜 = **idle 전이를 놓친 것**.

## 원인 (2026-07-10 진단)
1. `Resources/Hooks/codex-hook.ps1` 이 busy 파일에 `Set-Content -Value 'idle'` 로 **직접** 썼다.
2. `Set-Content` 는 파일을 0바이트로 truncate 후 값을 쓴다. truncate 직후 훅 프로세스가 중단되면
   (codex 훅 타임아웃/종료 레이스로 추정 — **정확한 트리거는 미확정**) **0바이트 빈 파일**이 남는다.
3. `CodexHookService.EmitBusy` 는 빈 값을 `return` 으로 무시만 했다 → 그 파일엔 이후 Changed 이벤트가
   더 안 와서 idle 전이를 **영영 놓침** → 스피너 stuck-ON.
4. **결정적 증거:** 문제 방(codex, 이름 "보더 하이라이트")의 busy 파일이 정확히 **0바이트**(정상은
   `running\r\n` 9바이트). 그 시각 `C:\devezLog\diag.log` 에 앱 종료/Dispose/재진입 이벤트 없음
   → 앱이 아니라 **훅 Set-Content 가 남긴 0바이트**.

## claude 는 왜 안 그런가 (참조 구현)
claude 훅(`TerminalSessionManager.cs` busyScript 의 `Write-State`)은 **원자적 write** 를 쓴다:
```powershell
$tmp = $path + '.' + [Guid]::NewGuid().ToString('N') + '.tmp'
Set-Content $tmp $value        # temp 에 완전히 쓴 뒤
Move-Item $tmp $path -Force     # 원자적 rename (같은 NTFS 볼륨)
```
중간 0바이트 상태가 없다. + 앱 레벨 `SessionBusyService` 의 적응형 reconcile 타이머(활성 4초/완전
유휴 30초 — `ReconcileActiveMs`/`ReconcileIdleMs`)가 파일시스템 진실
(main 플래그/subrun)로 stale 을 재수렴한다. **claude 는 훅+앱 이중 방어, codex 는 둘 다 없었다.**
claude busyScript 주석에 이미 *"직접 Set-Content 는 쓰기 도중 끊기면 손상/빈 파일이 남는다"* 고
명시돼 있음 — 알려진 현상.

## 수정
- **근본:** `codex-hook.ps1` 에 claude 와 동일한 `Write-State`(temp+`Move-Item`) 함수 추가,
  busy/lastmsg/session_id 쓰는 **4곳의 직접 `Set-Content` 전부 교체**. → 0바이트 원천 차단.
- **보조:** `CodexHookService.EmitBusy` 가 빈 값 읽으면 120ms 뒤 재확인, 그래도 비면 idle 로 확정
  (`ReEmitBusyAfterSettleAsync`) — 구버전 훅/잔여 경합 복구용. claude 의 waiting 재읽기 패턴 이식.
- 훅 스크립트는 앱 시작 시 `CodexHookInstaller.EnsureScriptInstalled` 가
  `%LOCALAPPDATA%\DevezCode\codex\hook.ps1` 에 덮어쓴다 → **빌드+앱 재시작해야 반영.**

## 재발 방지
훅/외부 프로세스가 방별 상태 파일(busy/lastmsg/waiting/session 등)을 쓸 때는 **직접 `Set-Content` 금지,
반드시 `Write-State`(temp+`Move-Item`) 원자적 쓰기.** 직접 쓰면 write 중단 시 0바이트가 남아 스피너
stuck-ON. 새 에이전트 추가 시 `.knowledge/에이전트추가규칙.md` §3 참고.

## 진단 팁
- 스피너 안 꺼짐 세션의 에이전트부터 확인(`workspace.json` 의 `Agent`). claude 면 reconcile 이 막으므로
  다른 에이전트(codex/opencode)일 가능성.
- 반대로 "busy 인데 스피너가 안 보임"은 버그가 아닐 수 있다 — **숨김 세션(`IsEffectivelyHidden`)은
  busy 여도 스피너가 강제 Collapsed** 되는 의도적 예외(`SidebarView.xaml` 트리거 순서).
- 해당 방의 busy 파일 크기 확인: `%APPDATA%\DevezCode\<agent>\busy\<room>.txt` 가 **0바이트면 이 버그**.
- codex busy 전이는 diag.log 에 안 남는다(claude 만 `busy[...] (hook)` 기록) — 진단이 오래 걸린 이유.
