# 생성 스크립트 인코딩 규칙 (한글 사용자명 경로에서 조용히 실패)

## 증상

특정 PC만 자동 업데이트가 안 됨. 앱은 종료되는데 새 버전으로 안 바뀌고,
"자동 업데이트 미적용" 안내(`--update-failed`)도 안 뜬다. 훅/세션추적도 같은 PC에서만 이상.

→ 그 PC의 Windows 사용자명이 **한글**(`C:\Users\김이영`).

## 원인

셸은 스크립트 파일 바이트를 자기 규칙으로 디코딩한다. `File.WriteAllText` 기본값은
BOM 없는 UTF-8 이라 스크립트에 박힌 한글 경로가 깨지고, `Copy-Item`/`Start-Process`가
전부 실패한다. 사용자명이 ASCII 면 UTF-8/CP949 결과가 같아 증상이 안 나타난다 → 재현 어려움.

## 실측 결과 (Windows 11, 한국어)

| 소비자 | 디코딩 규칙 | 필요한 기록 방식 |
|---|---|---|
| `powershell.exe` 5.1 (`-File`) | BOM 없으면 **시스템 ANSI(CP949)** | **BOM 있는 UTF-8** |
| `cmd.exe` (배치) | **그 시점 콘솔 코드페이지**. `chcp` 를 만나면 그 다음 줄부터 다시 디코딩 | 첫 줄 `@chcp 65001>nul 2>nul` (순수 ASCII) + 본문 UTF-8 |

- DevezCode ConPTY 콘솔 기본 코드페이지는 **949**, 외부 터미널은 **65001**.
  → 배치를 UTF-8 고정도, CP949 고정도 한쪽 환경에서 깨진다. **ASCII 프롤로그만** 양쪽에서 성립.
- BOM 은 `.cmd` 에 넣으면 안 된다(cmd.exe 가 첫 명령으로 오해).

## 규칙 (`Services/ScriptFile.cs`)

- `.ps1` → `ScriptFile.WritePs1` / `ScriptFile.Ps1`
- 앱이 소유한 ConPTY 에서 실행할 런치 배치 → `ScriptFile.WriteLaunchCmd`
  - **본문이 순수 ASCII 면 프롤로그를 붙이지 않는다** → 지금까지 정상 동작한 환경은 파일이
    바이트 단위로 종전과 동일해진다(코드페이지가 바뀌는 부작용 없음).
    roomId 는 32자 hex GUID, 배치에 박히는 경로는 `%APPDATA%\DevezCode\...` 라 사용자명이
    ASCII 면 본문 전체가 ASCII 다. 배치에 작업 디렉터리는 안 들어간다(ConPTY WorkingDirectory 로 전달).
  - 비ASCII 가 섞인 경우(한글 사용자명·한글 프로젝트 경로)에만 프롤로그를 붙인다 —
    그런 환경은 어차피 지금 깨져 있으므로 회귀가 아니라 수정이다.
- **남의 콘솔을 상속해 실행되는 `.cmd`**(codex/grok/kimi `state-hook.cmd`, agy `hook.cmd`)
  → 프롤로그 금지. 그 콘솔의 코드페이지를 바꿔 에이전트 TUI 렌더가 흔들린다.
  대신 **내용을 ASCII 로만 유지**해 인코딩 의존을 없앤다.

## 함정: 구버전 파일이 갱신되지 않음

훅 설치부는 `File.ReadAllText(path) != content` 로만 비교했다. BOM 없이 설치된 옛 파일은
내용 문자열이 같아 **영원히 재기록되지 않는다** → 수정해도 그 PC에서 버그가 남는다.
그래서 `ScriptFile.Ps1NeedsWrite` 가 **BOM 유무까지 확인**한다. 인코딩 규칙을 바꿀 때는
"이미 깔린 파일을 어떻게 갱신시킬지"를 항상 같이 설계해야 한다.

## 같은 함정: 작업용 임시 `.ps1` (AI/에디터가 만드는 스크립트)

앱이 만드는 스크립트뿐 아니라 **배포·유지보수 작업 중에 만드는 임시 `.ps1` 도 똑같이 걸린다.**
Claude Write 도구·대부분의 에디터는 기본이 **BOM 없는 UTF-8** → `powershell.exe` 5.1 이 CP949 로
읽어 **스크립트에 박힌 한글 리터럴이 깨진 채 실행된다.** 문법 오류가 없어 조용히 성공하는 게 최악.

실제 사고 (v1.22.6 배포, 2026-08-04): version.json 조립 `.ps1` 안의 새 업데이트 노트 한글이
깨져 나왔다. 라이브 JSON 에서 `ConvertFrom-Json` 으로 읽어온 **기존 이력은 무사**했으므로,
"이력은 정상인데 이번 버전 문구만 깨짐" 이 이 문제의 지문이다. 업로드 전에 발견해 사고는 없었음.

**대응 (둘 중 하나):**

1. **한글을 스크립트 밖으로 뺀다(권장).** 별도 `.txt`/`.json` 에 쓰고 스크립트에서 명시적으로 읽기:
   `[System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))`.
   `Get-Content` 은 안 된다 — 5.1 기본 인코딩이 ANSI 다.
2. `.ps1` 을 **BOM 있는 UTF-8** 로 기록한다(앱 코드라면 `ScriptFile.WritePs1`).

검증은 **파일을 직접 읽어서** 한다. 콘솔 출력은 코드페이지 때문에 정상이어도 깨져 보이고
깨져도 정상처럼 보일 수 있어 판단 근거로 쓸 수 없다.

## 검증 방법

한글 이름 폴더를 만들고, 콘솔 코드페이지를 949/65001 로 각각 바꿔 스크립트를 실행해
한글 경로 접근이 성공하는지 본다(래퍼 배치는 ASCII 로 두고 `chcp <cp>` 후 대상 호출).
BOM 없는 `.ps1` 은 `Get-Content : An object at the specified path ... does not exist` 로 실패한다.

## 관련

- 배포된 옛 버전은 이 버그가 담긴 스크립트를 쓰므로 **자동 업데이트로 못 넘어온다** →
  해당 PC는 인스톨러로 **수동 1회 재설치** 필요.
